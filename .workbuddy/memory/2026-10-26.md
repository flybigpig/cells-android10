## ServiceManager 核心作用

- 产出 `doc/ServiceManager_核心作用_Android10.md`（877 行，六段式 + 2 张 Mermaid + 速查表）。
- 定位：Binder 的「户籍科」，只做 name → uint32 handle 翻译，不参与业务通信；业务调用拿完 handle 后点对点直连。
- 五大作用：svclist 注册表、handle 0 锚点、SELinux add/find/list 闸门、acquire+death 保活、allow_isolated 管控。
- 用户态实测：`service_manager.c` main:391 / binder_open:406（mapsize 128K）/ become_context_manager:419 / binder_loop:451 / svcmgr_handler:256（switch:309）/ do_add_service:206（OVERRIDE:225）/ do_find_service:182 / svc_can_register|find|list:116|127|133 / svcinfo_death:165 / svclist:150。
- `frameworks/native/cmds/servicemanager/binder.c`（400 余行裸 ioctl 版，非 libbinder）：open:109（O_CLOEXEC:120、BINDER_VERSION:127、mmap:138）、become:164（EXT:169 优先、降级 SET_CONTEXT_MGR:175）、loop:455（BC_ENTER_LOOPER:465）、parse:252（BR_TRANSACTION:280、func:315、send_reply:320）、binder_call:389（BC_TRANSACTION:405）、bio_put_ref:592、bio_get_ref:707、reply 缓冲 256B:304。
- 内核：`binder_context_mgr_node:268`、`_uid:271`、`binder_ioctl_set_ctx_mgr:5184`（单例 5193 / SELinux 5198 / uid 5201 / 赋值 5223）、SET_CONTEXT_MGR_EXT:5336 / SET_CONTEXT_MGR:5348、**handle 0 特例分支 3337-3346**（不查 refs_by_desc）、`desc=0` 强制赋值 1929、退出清空 5740、设备初始化 6449。
- 客户端：`ProcessState::getContextObject:117`（`getStrongProxyForHandle(0):119`）、`defaultServiceManager:43`（:55）、`BpServiceManager:215`（getService:223 含 5s 重试:230 / checkService:254 / addService:271 / listServices:287）、Java `ServiceManager.getIServiceManager:105`。
- 关键机制：SM 返回的 handle 是 **SM 进程视角 desc**，驱动在 `binder_translate_handle:2852/2896` 改写成客户端视角；跨进程传 handle 必须经 `flat_binder_object`，裸传 uint32 会命中错号服务。
- ⚠ **本仓发现安全缺陷**：`service_manager.c:88` 的 `check_mac_perms` 结尾是 `return true;`（AOSP 原版为 `return allowed;`），SELinux service_manager 类校验恒通过；配合 `do_add_service:225` 的 OVERRIDE，任何 native 进程可顶替任意服务。已在文档 §6.1 标注。
- 版本坑：本仓 binder.c 带 `CONFIG_DRV_NS` 厂商定制（acontext[] 多 context、`INIT_OTHER_CONTEXT_MGR_HANDLE` 编址、`getMgrContextObject`），对照 AOSP 主线需注意 `#ifdef`。

## svcmgr_handler 逐行分析

- 产出 `doc/ServiceManager_svcmgr_handler_逐行分析_Android10.md`（828 行，六段式 + 3 张 Mermaid + 行号索引表）。
- 定位：ServiceManager 唯一业务函数，裸 C 回调（无 BnServiceManager::onTransact），被 `binder_loop` 串行调用。
- 函数内行号：签名 256 / 取 txn 269 / **target.ptr 校验 274** / PING 短路 277 / strict_policy 284 / worksource 285 / token 286 / **svcmgr_id 校验 291-295** / SELinux 热更新 297-307 / switch 309 / GET+CHECK 311-322 / ADD 324-335 / LIST 337-361 / default 362 / 写异常码 367。
- **`target.ptr == 0` 的因果链（关键发现）**：`binder.c:166` `memset(&obj,0)` → `obj.binder == 0` → 内核 `binder_init_node_ilocked:1479` `ptr = fp->binder = 0` → `node->ptr = 0` → `binder_thread_read:4760` `trd->target.ptr = target_node->ptr = 0` → 与 `BINDER_SERVICE_MANAGER(0U)` 相等。收包侧用 ptr，发包侧用 handle（union 两投影）。
- 返回值三态：GET 成功 `return 0`（reply 仅 flat_binder_object）/ ADD 成功 `break`→`:367` 写 uint32 0 / 任何失败 `return -1`→TF_STATUS_CODE。GET 失败靠 `fbo.hdr.type == 0` 表达空（BINDER_TYPE_* 无 0）。
- reply 约束：`binder.c:304` `rdata[256/4]` + `bio_init(...,4)` → offs 占 32B（64 位），**净 224B**；溢出静默（`BIO_F_OVERFLOW`）。
- 回包技巧：`binder_send_reply:209` 用 `__attribute__((packed))` 把 `BC_FREE_BUFFER` + `BC_REPLY` 合并成一次 ioctl；`status!=0` 走 `TF_STATUS_CODE`（`binder.h:295` = 0x08）只发 4 字节，`&status` 是栈地址、依赖同步 ioctl。
- 协议字段序（客户端 `Parcel::writeInterfaceToken:624` ↔ 服务端 284/285/286）：strictPolicy(i32) → workSource(i32) → token(String16)；SM 读后两段中前两段**读了就扔**（不做 outbound RPC）。
- 其余要点：PING 在 token 校验之前（`pingBinder` 发空 Parcel）；LIST 的 `-1` 表示"遍历结束"非错误，客户端靠 `err != NO_ERROR` 退出；GET 与 CHECK 服务端完全等价，客户端只用 CHECK；`bio_get_ref:707` 依赖 offs 数组、找不到静默返回 0。
- 本仓鉴权失效的具体落点：`:317` find、`:332` add、`:341` list 三条路径全部恒通过（承接 `service_manager.c:88 return true`）。

## Binder 服务发现完整闭环（注册 / 发现 / 直连）

- 产出 `doc/Binder_服务发现完整闭环_注册发现直连_Android10.md`（850 行，六段式 + 4 张 Mermaid + 对照表）。
- **核心纠正**：用户所述「客户端→SM→服务端→SM→客户端」不成立，SM 不做转发。真实为三段独立过程：①注册（服务端→SM，开机一次）②发现（客户端⇄SM，每客户端一次）③业务（客户端⇄服务端直连，N 次）+ ④失效通知（服务端死→SM→客户端）。
- **bootstrap 论证**：客户端要连 system_server 需 handle，handle 由 SM 给，连 SM 需 handle 0，handle 0 是内核硬编码特例（`binder.c:3337` 不查表）。故只可能有一个引导服务。
- **三个数字**（同一服务三进程三值）：服务端 `fbo.binder = JavaBBinder*`（指针）→ 驱动 `binder_translate_binder:2830` 改写为 SM 的 desc（存 `svcinfo.handle:229/237`）→ `binder_translate_handle:2896` 改写为客户端 desc → `BpBinder::create(handle):314`。desc 分配是「最小可用编号」非递增（`:1929-1936`）。
- 阶段①实测：`SystemServer.java:781` → `ActivityManagerService.java:2040/2042`（`addService("activity", this, allowIsolated=true)`）；native `main_surfaceflinger.cpp:132-134`；Java Proxy `ServiceManagerNative.java:147`（`writeStrongBinder:153`、`transact:156`）。
- 阶段②实测：`ActivityManager.java:4041` → `:4054` `ServiceManager.getService` → `:4055` `Stub.asInterface`；`WindowManagerGlobal.java:178-182`；`ServiceManagerNative.java:135` `checkService`。
- **`ProcessState::getStrongProxyForHandle:273` 关键注释**（`:288-305`）：context manager 是唯一"未持引用就要建 BpBinder"的对象，故对 handle 0 先发 `PING` 探测（`:308-309`）；官方承认非 race-free（`:299`），TODO 想取消 handle 0 特例。`BpBinder::create(handle):314`。
- 阶段③：`BpBinder::transact:217` → `IPCThreadState::transact:663` → 内核 `:3313-3336` 查 `refs_by_desc`，**不碰 SM**。铁证：SM 单线程（`binder_loop` 无 `BR_SPAWN_LOOPER`），不可能转发全系统流量。
- 阶段④：`BR_DEAD_BINDER`（`binder.c:342`）→ `svcinfo_death:165` → `handle=0:172`；客户端旧 handle 得 `BR_DEAD_REPLY`（`DEAD_OBJECT`），**不自动重连**。
- 补充要点：`getService` 有 5s 阻塞重试（`IServiceManager.cpp:230-249`，开机 100ms / 启动后 1s 一轮）；一个 `binder_proc` 可有 N 个 `binder_node`（system_server 注册 100+ 服务）；Java 服务 `JavaBBinder` 与 Native `BBinder` 在驱动眼里等价。
- 完整攻击链：SM 鉴权失效 → 阶段① `addService` 顶替名字 → 所有客户端 `getService` 拿到劫持者 handle → 业务直连攻击者（无需碰 SM 流量）。
