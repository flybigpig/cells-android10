## 一、AMS ANR 判定与处理全流程

### 1.1 重要更正：`handleApplicationANR` 在 Android 10 已不存在

全仓（`frameworks/`）grep `handleApplicationANR` **0 命中**。它是 Android 5~8 时代的 API，Q 上 ANR 处理重构为：

```
AMS.inputDispatchingTimedOut()  →  ProcessRecord.appNotResponding()
```

### 1.2 五类 ANR 触发源与超时阈值

| ANR 类型 | 阈值 | 常量定义 | 判定/触发点 |
|---|---|---|---|
| 输入调度（按键/触摸） | **5s**（instrumentation/wrapper 下 **60s**） | `ActivityTaskManagerService.java:314` `KEY_DISPATCHING_TIMEOUT_MS = 5*1000`；`:316` `INSTRUMENTATION_KEY_DISPATCHING_TIMEOUT_MS = 60*1000` | native `InputDispatcher` → `InputManagerCallback.notifyANR` |
| 前台广播 | **10s** | `ActivityManagerService.java:479` `BROADCAST_FG_TIMEOUT = 10*1000` | `BroadcastQueue.broadcastTimeoutLocked` |
| 后台/offload 广播 | **60s** | `ActivityManagerService.java:480` `BROADCAST_BG_TIMEOUT = 60*1000` | 同上 |
| 前台服务 | **20s** | `ActiveServices.java:125` `SERVICE_TIMEOUT = 20*1000` | `ActiveServices.serviceTimeout` |
| 后台服务 | **200s** | `ActiveServices.java:128` `SERVICE_BACKGROUND_TIMEOUT = SERVICE_TIMEOUT * 10` | 同上 |

### 1.3 判定主流程：`ProcessRecord.appNotResponding`（`ProcessRecord.java:1407-1600`）

Android 10 的 ANR **唯一实现主体**，所有触发源最终汇聚于此。

#### (1) 前置动作与去重（1413-1441）

### 4.4 核心恒等式


### 4.5 判定矩阵：dispatch 慢 = native 积压 还是 App 主线程卡？

| 观测组合 | 结论 | 下一步 |
|---|---|---|
| `waitQueue` 大 + **Java `mPendingInputEventCount` 大** | **App 主线程处理慢**（onTouch 重活、View 树深、锁竞争、GC） | traces.txt 主线程堆栈 + `deliverInputEvent` trace 段 |
| `waitQueue` 大 + **Java 链表 ≈ 0/1** + `mProcessInputEventsScheduled=true` 但不动 | **主线程卡死**（Looper 跑不到：长耗时、Binder 同步等待、死锁） | 主线程堆栈，典型 `BinderProxy.transact` / `Object.wait` |
| `outboundQueue` 大 + `inputPublisherBlocked=true` + `waitQueue` 停滞 | **socket 背压**，App 连 read 都做不到（彻底停摆） | 同上，已确认"完全卡死"而非"处理慢" |
| `waitQueue` 小但仍 ANR | 非吞吐问题：焦点窗口不存在、Key 串行化（`:1844`）、motion `waitQueue` 队头滞留（`:1866`） | 看 ANR Reason 字段 |
| `waitQueue` 大且全是 MOVE | **批处理延迟**，等 Choreographer 下一帧 | 属正常；`mUnbufferedInputDispatch` 可关闭批 |
| `mFinishQueue` 非空 | 反向背压，dispatcher 来不及读 finish | 少见 |

直接判据：
- ANR 日志里 `checkWindowReadyForMoreInputLocked` 会打印 `Outbound queue length: N. Wait queue length: M.`（1826-1828）。`N>0` = socket 塞住；`M` 大 = 已发出未回执。
- native 免费日志（`:4197-4203`，阈值 `SLOW_EVENT_PROCESSING_WARNING_TIMEOUT = 2s`，`:92`）：
  `Window 'xxx' spent X ms processing the last input event` —— 打出这条基本可断定 **App 侧处理慢**。
