## 2. 窗口树层次 / addWindow 流程 / performSurfacePlacement 主循环

### 2.1 窗口树层次

编译期泛型约束的父子链条：

```
RootWindowContainer extends WindowContainer<DisplayContent>
DisplayContent extends WindowContainer<DisplayChildWindowContainer>
TaskStack extends WindowContainer<Task>
Task extends WindowContainer<AppWindowToken>
AppWindowToken extends WindowToken
WindowState extends WindowContainer<WindowState> implements WindowManagerPolicy.WindowState
```

`DisplayContent` 内部有 `TaskStackContainers`（装 TaskStack）、`NonAppWindowContainers`（装系统 WindowToken）、壁纸控制器、InputMonitor 等。

`mChildren` 列表顺序即 Z 序，`assignWindowLayers` 把下标映射为 Surface layer。

### 2.2 addWindow 五阶段

1. **权限校验（锁外）**：`mPolicy.checkAddPermission(attrs, appOp)`。
2. **基础合法性（锁内）**：Display 存在/权限、防重复 client、子窗口 token 校验。
3. **WindowToken 解析**：无 token 按类型创建或返回 `ADD_BAD_APP_TOKEN`；token 存在校验类型匹配。
4. **创建 WindowState + openInputChannel**：死亡检测、`adjustWindowParamsLw`、`prepareAddWindowLw`、创建 InputChannel 对。
5. **挂树 + 焦点/输入同步**：越过"no errors"分界线 → `attach()` + `mWindowMap.put` → `mToken.addWindow` → `assignChildLayers` → `updateFocusedWindowLocked` → InputMonitor 同步。

关键：addWindow 结束明确注释"不做布局，必须 relayout 才显示"。

### 2.3 performSurfacePlacement 主循环

- `requestTraversal()`（WindowSurfacePlacer.java:197）post 到动画 Handler，去重；
- `performSurfacePlacement(boolean force)`（98–110）：defer 期间跳过，最多循环 6 次防死循环；
- `performSurfacePlacementLoop()`（112–184）：`mInLayout` 防递归、等待配置、强制移除内存紧张窗口、调 `mRoot.performSurfacePlacement()`；
- `RootWindowContainer.performSurfacePlacementNoTrace`（575–772）：UPDATE_FOCUS 预更新 → `openSurfaceTransaction` → `applySurfaceChangesTransaction`（布局+写 Surface）→ `closeSurfaceTransaction`（提交 SF）→ App 过渡 → 焦点二次更新 → resize/旋转/解冻 → 销毁不可见 Surface → 电源设置 post 到 Handler（避免持锁调 PMS）→ 输入窗口同步 → `scheduleAnimationLocked`。

**一句话**：performSurfacePlacement 是 WMS 的"渲染心跳"——防重入去重调度，在一个 Surface 事务内完成整棵树布局与提交，随后处理动画/过渡/焦点/输入同步。

## 7. WindowStateAnimator 如何管理 Surface 与动画

### 五级绘制状态机

```
NO_SURFACE(0) → DRAW_PENDING(1) → COMMIT_DRAW_PENDING(2) → READY_TO_SHOW(3) → HAS_DRAWN(4)
```

- `finishDrawingLocked()`（304）：DRAW_PENDING → COMMIT_DRAW_PENDING，请求布局；
- `commitFinishDrawingLocked()`（329）：→ READY_TO_SHOW，等 `atoken.canShowWindows()` 后 `performShowLocked()`（避免闪现）。

### Surface 创建/销毁

- `createSurfaceLocked()`（426–532）：幂等、初始 HIDDEN、处理 SECURE/OPAQUE/DONT_SCREENSHOT flags、`new WindowSurfaceController`。
- `destroySurfaceLocked()`（572–630）：支持 `mSurfaceDestroyDeferred` 延迟销毁（drag-resize 保留旧 surface），收尾置 `mDrawState = NO_SURFACE`。

### Surface 属性应用

`prepareSurfaceLocked` 中通过 `WindowSurfaceController.setPositionInTransaction`、`setMatrixInTransaction`（1043）、`applyCrop` 写入 SurfaceControl.Transaction，由 WMS 批量提交。

### 动画职责（Android 10 关键变化）

- `applyAnimationLocked`（1327–1393）：按 transit（ENTER/EXIT/SHOW/HIDE）选择动画资源，调 `mWin.startAnimation(a)`；
- **动画执行已迁移到 `SurfaceAnimator`**：`WindowContainer.startAnimation` → `mSurfaceAnimator.startAnimation`（114–130）创建 **leash**（SurfaceControl 代理层），把窗口 Surface reparent 到 leash，动画作用于 leash，结束 reset 销毁 leash；
- 职责边界：WSA 管绘制状态机/Surface 几何/选动画；SurfaceAnimator 管逐帧推进/leash/回调；WindowAnimator 管帧调度。

> 完整口述稿见对话原文，核心脉络：

## 10. InputManagerService 口述稿

"InputManagerService 是输入系统的 Java 层门面，继承 IInputManager.Stub，三层架构：Java 层、JNI 层、native 层。

Java 层：mPtr 持有 native NativeInputManager 指针；mHandler 运行在 DisplayThread；mWindowManagerCallbacks 与 WMS 对接焦点窗口。启动三步走：nativeInit → setWindowManagerCallbacks → systemRunning 后 nativeStart。

JNI 层：NativeInputManager 同时实现 InputReaderPolicyInterface 和 InputDispatcherPolicyInterface，做策略桥接。

native 层（InputManager.cpp）：装配单向流水线 EventHub → InputReader → InputClassifier → InputDispatcher → App，initialize 启动 Reader/Dispatcher 两条线程，均 PRIORITY_URGENT_DISPLAY。

IMS 不知道哪个窗口在前台，依赖 WMS 通过 WindowManagerCallbacks 同步的焦点/输入窗口决定投递目标。

一句话：IMS 是 Java 门面，真正流水线在 native inputflinger，JNI 做策略桥接，目标决定权在 WMS。"

## 11. 触摸事件从驱动到 App 完整链路口述稿

"完整链路：驱动 → EventHub → InputReader → InputClassifier → InputDispatcher → InputChannel → App。

驱动写 /dev/input 节点，EventHub 用 epoll 监听、getEvents 读 RawEvent。InputReader.loopOnce 调 processEventsLocked，把原始事件组装成 MotionEvent（DOWN/MOVE/UP、坐标、时间戳）。InputClassifier 对 motion 异步分类（DEEP_PRESS/AMBIGUOUS_GESTURE）打标，非 motion 透传。InputDispatcher.notifyMotion 进 dispatchOnce 主循环，靠 WMS 同步来的焦点/输入窗口列表选目标，enqueueDispatchEntryLocked 排入发送队列。目标窗口对应 InputChannel（一对 socketpair），序列化写入送到 App。App 主线程 Looper 经 JNI 的 NativeInputEventReceiver 回调 InputEventReceiver.dispatchInputEvent，ViewRootImpl.WindowInputEventReceiver 把事件放进输入管线（多个 InputStage），最终 View.dispatchTouchEvent → onTouchEvent，处理完 finishInputEvent 回传闭环。

一句话：驱动产生、EventHub 读、Reader 组装、Classifier 打标、Dispatcher 靠 WMS 信息选目标、socketpair 跨进程、ViewRootImpl 分发到 View。"

## 12. WMS 与 ATMS 关系口述稿

"Android 10 拆分后职责分离但高度耦合：ATMS 管逻辑（Activity/Task/Stack 调度、谁在前台），WMS 管表现（窗口树/Surface/动画/输入焦点）。

建立联系：SystemServer 创建 WMS 时传入 ATMS 实例，随后 setWindowManager 把 WMS 反向注入 ATMS 及 StackSupervisor/RootActivityContainer。引用方式不对称：ATMS 直接持有 WMS Java 对象（同包同进程），WMS 反向走 LocalServices 的 ActivityTaskManagerInternal 接口（依赖倒置），少数 IPC 语义用 IActivityTaskManager Binder 代理。

最重要的锁：两者共用同一把 mGlobalLock（ATMS 创建，WMS 通过 atm.getGlobalLock() 复用），保证 Activity 与窗口状态原子一致；铁律是持 mGlobalLock 不能同步调 AMS，否则死锁，一律 post 到 Handler；锁序由 LockGuard 监管，AMS 锁外层、WM 锁内层。

调用方向双向交替：ATMS 下令 WMS（setFocusedTask/updateFocusedWindowLocked/deferSurfaceLayout），WMS 汇报 ATMS（mAtmInternal.notifyActivityDrawn）。以启动 Activity 为例：ATMS 选 Task → 命令聚焦 → App addView → 绘制 → WMS 通知 drawn → ATMS 收尾。"

## 13. AMS 口述稿

"AMS 是 system_server 最核心服务，继承 IActivityManager.Stub。Android 10 拆分：Activity/Task/Stack 逻辑交给 ATMS，AMS 保留进程管理、OOM adj、Service/Broadcast/Provider、电量统计、AppOps、用户管理。

## 14. Zygote 口述稿

"Zygote 是所有 App 进程和 system_server 的父进程，核心是预热+fork、copy-on-write 共享内存。

启动：init 根据 init.rc 拉起，入口 ZygoteInit.main。禁止 fork 前创建线程（startZygoteNoThreadCreation）。preload 预加载 class、资源、共享库、WebView、图形驱动。gcAndFinalize。创建 ZygoteServer 注册 socket。forkSystemServer 子进程 run() 进 SystemServer.main，父进程继续。

## 15. Binder 口述稿

"Binder 是 Android 特有 IPC，四层架构：内核驱动、Native、Java Framework、AIDL 生成层。

内核驱动：/dev/binder，binder_open 建 binder_proc、binder_mmap 建接收缓冲区——一次拷贝（目标缓冲区与内核共享物理页）。binder_transaction 找 binder_node、拷贝数据、插入 todo 队列唤醒目标线程。事务约 1MB 上限，超限 TransactionTooLargeException，大对象走 ashmem/FD。

Native：ProcessState 进程单例（open_driver、mmap、线程池上限 15）；IPCThreadState 每线程一份，talkWithDriver 经 ioctl(BINDER_WRITE_READ) 收发，joinThreadPool 循环；BpBinder.transact 带 FLAG_ONEWAY 异步标志。

Java：Binder 服务端 onTransact 分发；BinderProxy 客户端代理；Parcel 序列化载体。

AIDL：生成 Stub/Proxy，客户端 Proxy 打包 Parcel 走 transact，服务端 Stub.onTransact 解包调用实现；oneway 生成 FLAG_ONEWAY。

一句话：一次拷贝的 IPC，内核搬运、Native 封装 ioctl、Java 暴露接口、AIDL 生成 Stub/Proxy。"

## 17. SurfaceFlinger onMessageReceived：INVALIDATE 与 REFRESH

```1759:1838:frameworks/native/services/surfaceflinger/SurfaceFlinger.cpp
void SurfaceFlinger::onMessageReceived(int32_t what) {
    switch (what) {
        case MessageQueue::INVALIDATE: { ... }
        case MessageQueue::REFRESH: { handleMessageRefresh(); break; }
    }
}
```

### INVALIDATE（准备阶段，1762–1831）

1. `populateExpectedPresentTime` + 掉帧统计（frameMissed/hwcFrameMissed/gpuFrameMissed）；
2. 动态刷新率（Smart90）、背压处理（miss 时 signalLayerUpdate 后 break 跳过本帧）；
3. **核心**：`handleMessageTransaction()`（事务生效）+ `handleMessageInvalidate()`（handlePageFlip latch 新帧）；
4. `updateCursorAsync`、`updateInputFlinger`；
5. `refreshNeeded` 才 `signalRefresh()` —— **无变化不重绘**。

### REFRESH（合成提交阶段，1879–1928）

`preComposition` → `rebuildLayerStacks` → `calculateWorkingSet` → 逐屏 `beginFrame/prepareFrame/doComposition` → `postFrame`（queueBuffer + present）→ `postComposition`（归还旧 buffer）→ 统计合成方式 → `mVsyncModulator.onRefreshed` → 清 mLayersWithQueuedFrames。

**一句话**：INVALIDATE 判断有无活要干并准备数据（事务+latch），REFRESH 真正画一帧并提交；前者按需触发后者。

## 18. 对应客户端处理：VSync 驱动 App 绘制与提交

闭环：SF 发 VSync → App 绘制 → queueBuffer → SF latch → 合成 present。

1. **接收 VSync**（Choreographer.java:921）：FrameDisplayEventReceiver.onVsync 把 VSync 包装成异步消息投主线程 Handler，`mHavePendingVsync` 去重。
2. **doFrame**（714–728）：五阶段回调 INPUT → ANIMATION → INSETS_ANIMATION → TRAVERSAL → COMMIT。
3. **注册遍历**（ViewRootImpl.java:1734）：scheduleTraversals 插同步屏障（postSyncBarrier）、postCallback(TRAVERSAL, mTraversalRunnable)。
4. **执行遍历**（1757/1989）：doTraversal 移除屏障 → performTraversals（measure/layout/draw，可能 relayoutWindow）。
5. **绘制提交**（3784）：`mThreadedRenderer.draw` → RenderThread 渲染 → queueBuffer 到 BufferQueue（即 SF latch 的 buffer）；软件路径 unlockCanvasAndPost。
6. **完成回执**（3461）：`mWindowSession.finishDrawing(mWindow)` → WMS → WindowStateAnimator.finishDrawingLocked（DRAW_PENDING→COMMIT_DRAW_PENDING）。

两个关键机制：**同步屏障+异步消息**保证绘制不被打断；**BufferQueue 解耦**生产消费、支持双/三缓冲并行。

## 19. WMS 通知 SF 触发 INVALIDATE 的完整链路

WMS 不直接调 SF 的 INVALIDATE，而是通过 Surface 事务提交间接触发：

```
WMS performSurfacePlacement
 → openSurfaceTransaction/closeSurfaceTransaction（SurfaceControl 全局事务）
 → mTransaction.apply()（SurfaceComposerClient.cpp:441）
 → Binder setTransactionState（SF.cpp:3850）
 → applyTransactionState → setClientStateLocked 置 eTraversalNeeded/eTransactionNeeded
 → setTransactionFlags（3751）检测新标志
 → signalTransaction（1464）→ mEventQueue.invalidate()
 → MessageQueue::invalidate（158）= mEvents->requestNextVsync()
 → 下一个 VSync → eventReceiver → dispatchInvalidate
 → onMessageReceived(INVALIDATE)
```

关键设计：
- `setTransactionFlags` 只在 `(old & flags)==0`（新标志）时唤醒，避免重复；
- `signalTransaction` 与 `signalLayerUpdate` 都汇聚到 `mEventQueue.invalidate()`；
- `invalidate()` 不立即发消息，而是请求下一个 VSync，保证事务在 VSync 边界消费、不撕裂；
- `dispatchInvalidate` 用 eventMaskInvalidate 原子去重，一个 VSync 一条消息。

## 20. AOSP 事务（Transaction）机制全景

### 两个语境

- Binder Transaction（IPC 事务，前面已讲）；
- **Surface Transaction**（一批窗口改动的原子提交单元）——本节重点。

### 为什么需要

减少 IPC 次数、避免中间态可见、与 VSync 对齐。

### 两层 API

**局部事务**（`SurfaceControl.Transaction`，SurfaceComposerClient.h:288）：

```288:315:frameworks/native/libs/gui/include/gui/SurfaceComposerClient.h
    class Transaction {
        std::unordered_map<sp<SurfaceControl>, ComposerState, SCHash> mComposerStates;
        SortedVector<DisplayState> mDisplayStates;
        ...
        bool mAnimation = false;
        bool mEarlyWakeup = false;
        int64_t mDesiredPresentTime = -1;
```

方法：`apply`、`merge`、`show/hide`、`setPosition`、`setSize`、`setLayer`、`reparent`、`setBuffer` 等。

**全局事务**（SurfaceControl.java:965/994）：`openTransaction`/`closeTransaction`，全局单例 + 嵌套计数 `sTransactionNestCount`，最外层 close 才 apply。WMS 的 open/closeSurfaceTransaction 封装它。

### 四阶段生命周期

1. **收集**：setXxx 写入 mComposerStates 的 layer_state_t（s.what 位标记变更字段），零 IPC；merge 可合并多个事务。
2. **提交**：apply() 打包 Vector<ComposerState>，一次 Binder `sf->setTransactionState(..., applyToken, flags)`。
3. **SF 应用**：setTransactionState 入队或 applyTransactionState → setClientStateLocked 逐项应用 → 置 transactionFlags → setTransactionFlags。
4. **生效+回调**：signalTransaction → invalidate → 下个 VSync 的 INVALIDATE → handleTransaction 生效 → TransactionCompletedListener 回调。

### 三个语义标志

| 标志 | 作用 |
|---|---|
| `eSynchronous` | apply 阻塞等 SF 应用完 |
| `eAnimation` | 动画帧顺序保证 |
| `eEarlyWakeup` | 事务在 VSync 前更早开始，降低延迟 |

### 原子性四层体现

客户端批量收集 → 一次 Binder → SF 持 mStateLock 批量应用 → 统一在 VSync 帧边界生效。

### WMS 事务模式

- 全局批量：open/closeSurfaceTransaction 包裹整棵树改动；
- 局部事务：mTransaction.apply()（WMS:5613）；
- 合并：mergeToGlobalTransaction。

**一句话**：Surface Transaction 是一批窗口改动的原子提交单元——客户端链式收集零 IPC，apply 一次 Binder 提交，SF 锁内批量应用置标志，signalTransaction→invalidate→下个 VSync 生效，核心是减少 IPC、避免中间态、与 VSync 对齐。

## 21. 窗口属性修改后通知 SF

**核心结论**：ATMS 决定"改哪个窗口的什么属性"，WMS 把改动翻译成 Surface 事务中的 `layer_state_t` 字段变更，Binder 一次提交给 SF；SF 在 `setClientStateLocked` 按 `what` 位标记逐项应用、置事务标志，下个 VSync 的 INVALIDATE 阶段生效并合成。

### 三种提交通道

1. **全局事务**：`performSurfacePlacement` 中 `openSurfaceTransaction()`/`closeSurfaceTransaction()` 包裹整棵树属性修改；
2. **局部事务**：`mTransaction.apply()` 显式提交；
3. **buffer 通道**：App RenderThread 直接 `queueBuffer` 到 BufferQueue，走 `signalLayerUpdate`（不经 WMS 事务）。

### 按属性映射表

| 属性 | WMS 侧 API | 事务字段 | SF 侧应用 |
|---|---|---|---|
| 位置 | `setPositionInTransaction` → `setPosition`(行234) | `ePositionChanged` | `layer->setPosition`(4096) |
| 尺寸 | `setBufferSizeInTransaction` → `setBufferSize`(299) | `eSizeChanged` | `layer->setSize`(4137) |
| Z 序 | `setLayer`/`setRelativeLayer`（assignChildLayers） | `eLayerChanged`/`eRelativeLayerChanged` | `setLayer` + 重排 `layersSortedByZ`(4101/4119) |
| 裁剪 | `setCropInTransaction` → `setWindowCrop`(181) | `eCropChanged` | `layer->setCrop`(4260) |
| 变换矩阵 | `setMatrixInTransaction`(252) | `eMatrixChanged` | `layer->setMatrix`(4176) |
| alpha | `mWinAnimator.mAlpha` | `eAlphaChanged` | `layer->setAlpha`(4142) |
| 可见性 | `hide()`→`transaction.hide`(153)/`show()`(444) | `eFlagsChanged`(HIDDEN) | `layer->setFlags`(4183) |
| buffer | App `queueBuffer`（非 WMS） | `eBufferChanged` | `layer->setBuffer`(4327) |

几乎所有属性应用后置 `eTraversalNeeded`；Z 序变化额外置 `eTransactionNeeded`（列表本身变了）。

### 两类触发源

- **WMS 主动改属性**：`performSurfacePlacement` → `prepareSurfaceLocked` → `WindowSurfaceController.setXxxInTransaction`，在 open/closeTransaction 区间累积后一次提交；Z 序由 `assignChildLayers` 计算；可见性由 WSA 五级状态机决定 show/hide。
- **App 提交 buffer**：BufferLayer `onFrameAvailable` → `signalLayerUpdate()` → `mEventQueue.invalidate()` → `handlePageFlip/latchBuffer`。**WMS 不传 buffer，只管几何/层级/可见性等元数据**。

### SF 侧统一模式

`what` 位标记 → `layer.setXxx` → 若状态真改变则置 flag → 汇总 `setTransactionFlags`（3981）→ `signalTransaction()` → `mEventQueue.invalidate()` → 下个 VSync INVALIDATE 生效。

### ATMS 角色（决策层）

ATMS 不直接操作 Surface，经 WMS 本地接口下达决策：`setFocusedTask`/`updateFocusedWindowLocked`（焦点→Z序/可见性）、`notifyActivityDrawn`/App transition（可见性/alpha/动画）、`setAppFullscreen`/`setDockedStackResizing`（尺寸/位置/裁剪）、`deferSurfaceLayout/continueSurfaceLayout`（批量原子更新）。

### 属性事务 vs buffer 事务

| 维度 | 属性事务（元数据） | buffer 事务（像素数据） |
|---|---|---|
| 发起方 | WMS（代表 ATMS 决策） | App（RenderThread） |
| 通道 | `Transaction.apply` → `setTransactionState` | BufferQueue `queueBuffer` |
| 唤醒 | `signalTransaction`→`invalidate()` | `onFrameAvailable`→`signalLayerUpdate()` |
| 处理 | `handleMessageTransaction` | `handleMessageInvalidate` |
| 内容 | 位置/尺寸/Z序/裁剪/矩阵/alpha/可见性 | GraphicBuffer |

两者最终都汇聚到 `mEventQueue.invalidate()`，在下个 VSync 的 INVALIDATE 汇合、REFRESH 合成 present。

**一句话**：ATMS 做决策、WMS 翻译成 Surface 属性事务（位标记+layer_state_t）、Binder 提交、SF 按位应用置标志、invalidate→下个 VSync 生效；buffer 走 App→BufferQueue 独立通道，两者在 INVALIDATE 汇合。
